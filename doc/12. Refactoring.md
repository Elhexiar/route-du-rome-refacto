## Refactorisation

### Pourquoi cette refactorisation ?

L'application fonctionnait déjà dans ses grandes lignes, mais son organisation rendait les corrections difficiles. Une partie importante du comportement était regroupée dans `GameManager`, tandis que plusieurs vues et services allaient chercher directement leurs dépendances dans ce singleton.

Ce fonctionnement avait plusieurs conséquences :

- les classes étaient difficiles à tester seules ;
- l'ordre de création des contrôleurs n'était pas toujours évident ;
- une vue pouvait modifier directement l'état métier ;
- les services connaissaient parfois les composants HTML qu'ils devaient afficher ;
- l'ajout d'une fonctionnalité obligeait à modifier plusieurs endroits peu liés entre eux ;
- les tests devaient préparer un état global avant de pouvoir instancier une classe.

Le but de la session n'était pas de changer le jeu, mais de rendre son fonctionnement plus lisible et plus facile à faire évoluer. La priorité a donc été donnée à l'injection de dépendances, à la séparation des responsabilités et à une communication plus explicite entre les différentes parties de l'application.

---

### Situation avant le refactoring

Dans la version précédente, `GameManager` jouait plusieurs rôles à la fois :

- stockage global des contrôleurs ;
- création des contrôleurs ;
- création de certaines vues ;
- point d'accès utilisé par les vues et les services ;
- initialisation de l'application dans le navigateur.

Une classe pouvait donc avoir un constructeur apparemment simple, puis récupérer en réalité une grande partie de son environnement dans `GameManager`. Par exemple, un service pouvait avoir besoin d'un contrôleur de héros, de la carte, de l'élément HTML principal et d'un autre service, sans que ces dépendances soient visibles dans son appel de création.

Le problème n'était pas uniquement l'existence du singleton. Le vrai problème était que le singleton masquait le graphe de dépendances. Il devenait difficile de répondre simplement à des questions comme : « qui crée cette vue ? », « quel contrôleur est utilisé ici ? » ou « pourquoi cette classe fonctionne-t-elle dans le navigateur mais pas dans un test ? ». Ca rendait le fait de se rememorrer et se deplacer dans la codebase insuportable.

L'initialisation asynchrone des données accentuait encore cette difficulté. Les héros et les PNJ sont chargés depuis `config.json`, alors que plusieurs vues doivent être créées autour de ces données. Le moment où une vue était créée pouvait donc modifier son comportement.

---

### Situation après le refactoring

La création de l'application est maintenant centralisée dans `ApplicationContainer`. Cette classe constitue le point de composition de l'application : elle crée les dépendances dans le bon ordre, puis les transmet explicitement aux contrôleurs, aux services et aux vues.

L'ordre de création est désormais lisible :

1. création de l'`EventBus` ;
2. création des contrôleurs de PNJ et de héros ;
3. création de la carte ;
4. création du contrôleur d'expérience et de ses services ;
5. création du contrôleur de dialogues ;
6. création de la vue de sélection des héros ;
7. création du service de notifications ;
8. création de la vue de sélection dans l'en-tête.

Les dépendances importantes sont passées dans les constructeurs ou dans un objet `runtime` explicite. Une classe n'a donc plus besoin de consulter `GameManager` pour découvrir son environnement.

Le chargement asynchrone des héros est également mieux pris en compte. La vue d'accueil est initialisée avec le contrôleur de dialogue déjà créé, puis attend le chargement des héros si nécessaire. Cela a notamment corrigé le problème suivant : la sélection d'un héros masquait la vue d'accueil, mais ne lançait pas correctement son dialogue de présentation.

---

### Comparaison synthétique

| Avant                                                                           | Après                                                                                   |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `GameManager` créait lui-même la majorité du graphe applicatif.                 | `ApplicationContainer` est le seul endroit qui compose l'application.                   |
| Les dépendances étaient souvent récupérées implicitement dans un singleton.     | Les dépendances sont transmises explicitement.                                          |
| Les services et les vues étaient fortement liés à `GameManager`.                | Les classes de production n'utilisent plus le singleton.                                |
| Les notifications étaient déclenchées directement par les services et les vues. | Les services émettent des événements et `NotificationService` pilote les notifications. |
| `QuestService` créait les toasts.                                               | En mode applicatif, les toasts sont créés et affichés par `NotificationService`.        |
| `BadgeService` créait et affichait le carnet de badges.                         | `NotificationService` écoute la collecte d'un badge et affiche le carnet.               |
| La fermeture d'une vue pouvait compléter directement une quête.                 | `DialogueController` décide de la complétion de la quête du PNJ.                        |
| Plusieurs méthodes existaient en double, en version minuscule et majuscule.     | Les méthodes canoniques utilisent la convention camelCase.                              |
| Certaines méthodes d'interface levaient une erreur ou ne faisaient rien.        | Les méthodes non implémentées et sans appel ont été retirées.                           |
| Les tests dépendaient parfois de l'état global du singleton.                    | Les tests injectent leurs dépendances directement.                                      |

---

### Mise en place de l'injection de dépendances

Les contrôleurs et les services ont été progressivement débarrassés de leurs accès directs à `GameManager`.

Les classes suivantes fonctionnent maintenant avec des dépendances injectées :

- `DialogueController` ;
- `MapController` ;
- `ExperienceController` ;
- `QuestService` ;
- `BadgeService` ;
- `DialogueView` ;
- `WelcomeHeroSelectionView` ;
- `HeaderHeroSelectionView` ;
- `NotebookView` ;
- `QuestCompletedToast` ;
- `EndToast` ;
- `MapView` et `Marker`.

Le cas des services de quêtes et de badges a demandé une transition progressive. Le comportement historique a d'abord été conservé pour ne pas casser les tests et les écrans existants, puis les responsabilités d'affichage ont été déplacées vers `NotificationService`. Les anciennes propriétés de toast restent accessibles pour les scénarios de compatibilité, mais le chemin principal de l'application passe par l'`EventBus`.

---

### Communication par événements

Un `EventBus` a été ajouté pour éviter que chaque service connaisse directement les composants qui réagissent à ses changements. ( decoupling, on a des layers beaucoup plus distinct et beacoup moins de références dans tous les sens )

Les événements utilisés couvrent notamment :

- la complétion d'une quête ;
- le gain d'expérience ;
- le changement de niveau ;
- la collecte ou le retrait d'un badge ;
- le changement de héros ;
- le chargement des héros et des PNJ ;
- l'affichage d'une notification ;
- le démarrage et la fin de la partie.

Les noms d'événements sont regroupés dans `AppEvents`. Les payloads associés sont décrits dans `AppEventPayloads` et servent de référence commune aux services et aux consommateurs. Le `EventBus` reste volontairement permissif dans la version actuelle afin de conserver la compatibilité avec le code existant. Un typage plus strict a été étudié, mais il ajoutait une couche de contraintes et de conversions sans bénéfice immédiat pour le périmètre du projet.

Le fonctionnement est désormais le suivant :

Exemple completion de quete

```text
QuestService
	|
	|  QUEST_COMPLETED / NOTIFICATION_SHOW
	v
EventBus
	|
	v
NotificationService
	|
	+--> QuestCompletedToast
	+--> EndToast
	+--> NotebookView
```

Le service métier conserve donc la responsabilité de modifier l'état et d'émettre l'information. La décision d'afficher un élément d'interface appartient à un service dédié.

---

### Responsabilités déplacées

#### Quêtes et expérience

`ExperienceController` est devenu la référence pour l'expérience et le niveau courant. Lorsqu'une récompense est attribuée, il met à jour l'expérience, recalcule le niveau et émet les événements correspondants.

`QuestService` conserve la création des quêtes et des badges liés aux PNJ. Lorsqu'une quête est terminée, il met à jour le PNJ, attribue l'expérience, collecte le badge associé et signale l'événement de complétion. (Il y a encore trop de responsabilité ca serait bien de cahnger cela plus tard ou de diviser les responsabilité)

#### Dialogues

`DialogueView` ne complète plus directement une quête lorsqu'une présentation de métier est fermée. Elle transmet maintenant l'action au `DialogueController`, qui retrouve la quête associée au PNJ et la complète. La vue reste ainsi centrée sur l'affichage et les interactions utilisateur.

#### Notifications

`NotificationService` possède les vues de notification et s'abonne aux événements. Cette séparation évite que `QuestService` et `BadgeService` créent eux-mêmes des éléments d'interface. (en plus j'oubliais toujours ou je mettait les toast maintenant c'est clair)

#### Sélection du héros

La vue d'accueil reçoit maintenant le contrôleur de dialogue déjà construit. Lorsqu'un héros est choisi, son dialogue de présentation est réinitialisé, la vue de dialogue reçoit le héros comme interlocuteur, puis elle est affichée.

---

### Nettoyage des méthodes et des interfaces

La refactorisation a également permis de retirer plusieurs doublons qui venaient d'une ancienne convention de nommage : `SwitchHero` et `switchHero`, `AddNpc` et `addNpc`, ou encore les méthodes de carte en double.

Les méthodes non implémenter ont aussi été supprimeés.

---

### Conservation de `GameManager`

`GameManager` n'est pas supprimé du projet. Il reste disponible dans la console du navigateur pour faciliter les tests manuels et l'inspection de l'état du jeu.

En revanche, il ne construit plus une seconde application. `ApplicationContainer` crée les vrais contrôleurs, puis `main.ts` les lie à `GameManager`. Ainsi, les commandes de console observent les mêmes instances que celles utilisées par l'interface.

`ConsoleTestController` regroupe les actions utiles pour les tests manuels : affichage des toasts, ajout d'expérience, montée de niveau, complétion de quêtes, collecte de badges, réinitialisation de la progression et affichage des dialogues.

La méthode `resetProgress()` réinitialise également les dialogues, les badges, les quêtes, l'état des PNJ, l'expérience et le niveau. Le singleton reste donc un outil de diagnostic, mais il n'est plus une dépendance cachée du code applicatif.

---

### Tests et vérifications

Les tests ont servi de garde-fou pendant toute la transition. Chaque modification importante a été suivie d'une compilation et d'une exécution de la suite de tests.

La suite finale comprend :

- 16 fichiers de tests ;
- 56 tests réussis ;
- une compilation TypeScript réussie ;
- un build Vite réussi.

Les tests portent notamment sur les entités de dialogue, les contrôleurs de héros, de PNJ et de carte, les services de quêtes et de badges, ainsi que le `ConsoleTestController`.

Quelques messages restent visibles dans les tests lorsque `QuestService` est créé sans interface graphique : `EndToast is not initialized`. Ils correspondent au scénario de compatibilité sans élément HTML et ne provoquent pas d'échec. Ils pourront être supprimés plus tard en remplaçant ces appels par des assertions sur les événements émis.

---

### Bilan

La différence principale entre les deux versions ne se résume pas au remplacement d'un singleton par une autre classe. L'application est maintenant composée explicitement, les dépendances sont visibles, et les changements d'état peuvent être communiqués sans créer de lien direct entre le métier et l'interface.

Le projet conserve son fonctionnement sans framework et sans backend supplémentaire. La structure est simplement plus nette : les contrôleurs coordonnent, les services portent les règles métier, les vues affichent et le container assemble l'ensemble.

`GameManager` reste volontairement disponible pour la console, mais le code de production n'a plus besoin de lui pour fonctionner. C'est le compromis retenu entre une architecture plus propre et un outil de test manuel pratique pendant la finalisation du projet. on s'est au moins débarasser du fameux singleton GodObject.
